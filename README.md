# reclaude-share-billing

多人合租几个 [ReClaude](https://reclaude.ai) 账号的**席位分配 + 用量计费**系统：
选账号、批准登录、记 device_id、按请求流水记账、独立管理设备下线、按租期成本分摊出账。

Seat sharing + usage billing for shared ReClaude accounts: assign devices, meter per-request usage,
evict the least-recently-used device when slots run out, split the account cost by weighted usage.

形态：Telegram Bot（管理员 / 用户）+ SQLite + 定时采集器。零第三方框架依赖（只有 `cryptography`）。

```
用户 ──/login 授权链接──▶ Bot ──approve──▶ ReClaude ──▶ 设备绑定到人
                            │
                            └── 每 5 分钟 ──拉请求流水──▶ SQLite ──▶ 账单
```

## 为什么不是"中转计费"

ReClaude 不发模型 API key：它给每个人分配真实的 Anthropic 订阅账号，Claude Code 直连官方。
能用来计费的只有两样东西 —— **设备名额**（每账号 4 台）和**后台的请求流水**（每条带唯一 id、token 分项和美元成本）。

## 已实现的能力

- **账号池**：管理员提交邮箱+密码，密码 Fernet 加密落库；每账号一把锁串行调用，会话 cookie 每次响应回写，401 自动用密码重登
- **开通**：用户发 `reclaude login` 的授权链接 → `describe` 取机器信息 → 选账号 → `approve`（设备名=用户）→ 登记 `device_id`；设备延迟出现时批准后自动认领，历史 `unknown` 设备不占席位
- **独立撤销**：登录分配不会触发 revoke；管理员主动撤销可绕过闲置保护，撤销前采集用量。
- **采集**：按账号时间窗翻页拉请求流水，请求 id 主键幂等；每轮把未归因请求回填到人；`pending` 定价自动补价
- **计费**：`加权用量 = cost_usd × 模型倍率`，`单价 = 租期成本 ÷ Σ加权（含未归属用量）`；已归属用户金额之和 + 待认领份额 = 账号成本，未归属用量不转嫁给其他人
- **Bot**：管理员 + 用户命令，白名单 chat，密码消息即时删除，写操作默认 `dry_run`

## 实测对账

拿一个真实账号跑 7 天窗口：**11,241 条请求，57 页**，本库按设备汇总与后台 `usage/stats` 的 `total_usd` **逐台完全一致**（差 0.0000），
包括两台**已 revoke、已从设备列表消失**的设备（54254 / 54243）—— 设备撤销后流水仍可查，账不会丢。

## 快速开始

```bash
pip install cryptography            # 唯一外部依赖

# 1) 配置
mkdir -p /opt/data/state/reclaude-billing
cp config.example.json /opt/data/state/reclaude-billing/config.json
#    填 bot_token（@BotFather 新建 bot）、admin_ids、allowed_chat_ids

# 2) 加账号（交互式也可在 bot 里 /account_add）
python3 -m app.cli account-add --id ultra-a --email you@example.com --password '***'
python3 -m app.cli units
# 从 units 输出选择组织下的上游订阅账号，不能使用登录标签 ultra-a
python3 -m app.cli period-add --unit 25693:7989 \
    --start 2026-11-01 --end 2026-11-30 --cost 2200

# 3) 配置模型倍率
python3 -m app.cli rate 'claude-opus-*' 1.5
python3 -m app.cli rate default 1.0

# 4) 跑一轮采集 + 出账
python3 -m app.cli sync
python3 -m app.cli report --start 2026-11-01 --end 2026-11-30

# 5) 起 bot（长轮询 + 后台采集循环）
scripts/run_bot.sh
```

用户：`/login <授权链接>` `/me` `/devices` `/bill [起 止]` `/help`

管理员：`/accounts` `/account_add` `/account_del` `/units` `/period add` `/period assign` `/periods` `/rate` `/rates`
`/revoke <账号:设备id>` `/bind <账号:设备id> <tg_user_id>` `/sync` `/report [起 止] [save]` `/health` `/dryrun on|off`

## 计费口径

计费单元使用本地稳定席位 ID，例如 `25693:seat1`，成本按组织内的席位配置。上游账号 ID 仅作为流水归属映射，换号后保留历史映射。持续观测为单席位的组织，当前账号替换时自动沿用同一席位；多席位或未知历史账号无法可靠匹配时保持待核对，用 `/unit_link 计费单元ID 上游账号ID` 明确关联，不猜测、不自动合并成本。登录邮箱仅为采集入口。

`/units` 自动显示组织到期时间并保留变更历史。仅对登录用户拥有的组织读取并校验订阅开始时间；其他组织的 `me.subscription.period_started_at` 可能串组织，不能直接采用。无法确认首期开始时间时需手动填写，不从到期时间倒推。

- 首期自动时间：`/period add 25693:seat1 auto auto 850`，管理员只需确认金额。
- 手动首期：`/period add 25693:seat1 2026-10-13T19:33 2026-11-12T19:33 850`。
- 续费：`/renew 25693:seat1 30 850`，从最后一个已配置周期的结束时刻接续 30 天。同一条 Telegram 消息重试不会重复续费。
- 换号补偿：`/period extend 租期ID 2026-11-13T19:33`，延长原周期但不增加成本。上游到期延长只自动记录，不据此判断续费或改账。

时间默认北京时间。带时间的周期采用 `[开始, 结束)`，支持分钟输入并保留自动读取的更高精度；相邻周期交界请求只计一次。旧的纯日期周期仍包含结束日期全天，续费从次日零点接续，不伪造旧记录精度。

- `/account_add` 只收集邮箱、密码和标签，不再配置成本。
- `/units` 查看发现的当前及历史订阅账号。
- `/period add 25693:7989 2026-11-01 2026-11-30 2200` 为明确的订阅配置成本。
- 升级保留旧租期，但不参与新分摊；先 `/periods` 查看旧租期 ID，再 `/period assign 旧租期ID 25693:7989` 指定归属，费用不会复制。
- 升级会一次性重置采集水位，从头回读以补齐此前未保存的上游账号 ID；无法从上游恢复归属的流水保持待核对，禁止保存不完整账单。旧账单快照保留并标为 `legacy`，不会当作新口径账单覆盖。
- `idle_split=even` 仅使用本订阅、本期已归属请求中的用户；不会把登录账号可见的其他订阅设备用户拉来均摊。没有可确认的用户时保留未分摊。

```
每条请求     w = cost_usd × multiplier(model)       # 隐藏倍率，按模型全局配置
每个账号期   p = 租期成本 ÷ Σw                       # 分母含未归属（user_id 为空）的 w
每人账单     Σ_账号 ( 自己的 Σw × p )
待认领       Σw_未归属 × p                           # 单独挂账，不进个人账单
```

- 总额 = 账号成本（已归属用户之和 + 待认领份额）；倍率只改变"谁承担多少"
- 未归属用量按同一单价折算成「待认领」，不摊到已归属用户头上
- 未配倍率的模型按默认值计，并在 `/rates` 和账单里单列
- `ignored` / `not_billable` 的请求不计费，也不计入未定价/超时统计；`pending` 超窗口仍在账单里单列
- 同一区间重新出账会覆盖旧快照，不会出两套账单
- 期未结束 → `provisional`；账号没配租期 → `incomplete`；请求落在租期外 → `uncovered`

## 已知边界

- 首次自动采集从 `since=0` 开始，拉取上游仍保留的全部历史；完成后才转入水位增量采集。升级后会一次性重置旧采集水位和续页位置，自动补齐过去只采 24 小时的缺口；已有流水、归属和账单保留，按请求 ID 去重。

- Bot 与采集线程使用独立的 SQLite 连接和事务；同账号的采集、撤销、会话操作共用锁。独立进程之间不共享这把锁，不要同时启动多个 bot/CLI 采集进程操作同一账号。
- 登录使用每次授权的随机设备名标记，只自动认领标记一致、批准前不存在的活跃设备。上游改写名称、旧版本遗留待认领记录或等待超过 10 分钟时，需要管理员核对实际设备并 `/bind`；`/health` 会列出待核对用户。
- 全局采集达到页数上限时，将固定时间窗和下一页 cursor 保存到 `sync_progress`，下轮或重启后继续；全部读完才推进水位。升级启动时自动创建此表。
- 自动撤销会重新读取上游设备活跃时间并结合本地最新流水检查；无法确认闲置时取消操作。管理员显式强制撤销仍可绕过闲置检查。

- 后台 API **没有官方文档**（`DESIGN.md` 附录是逆向 + 实测结果），随时可能变；解析是防御式的
- 采集粒度：增量轮询 5 分钟一次；首次回补 7 天约 3.5 分钟（上游延迟，每账号串行）
- 账号开 MFA 时无法自动重登，账号会标记 `mfa_required` 等管理员处理
- 撤销后的设备记录仍在流水里可查，但 `device_id → 人` 的映射必须在撤销前登记（`/bind` 可补）

## 安全

- 密码 Fernet 加密，key 与库分离（`secret.key` 0600）；Bot 收到密码消息后立即删除
- 所有写操作（approve / revoke）默认 `dry_run`，`/dryrun off` 才真实执行
- Bot 只响应白名单 chat，非白名单消息只记一行日志、不回复

### 额度均衡分配

`app/allocation.py` 独立读取并排序各登录账号自有组织内的当前账号，不调用撤销策略；`app/evictor.py` 独立负责撤销与闲置检查。登录不再为腾名额下线设备。

先排除设备名额不足、订阅过期和任一已知额度窗口耗尽的账号。读取 5 小时、7 天及细分模型额度，超过 15 分钟或已跨重置时刻的快照尝试刷新；无法得到新额度时降级为候选末位，不当作零使用量。排序分数为 80% 最大窗口使用比例 + 20% 最近 7 天已采集美元用量归一化值（Max 5x / 20x 分别除以 5 / 20，再除候选中最大值），分数越低越优先。同组织账号的多个采集入口去重，不以设备数量代替用量；设备数量仅作同分排序。

这是新登录分配，不会迁移已有设备，所以用量差异会逐渐改善。套餐倍率仅作相对负载权重，不代表精确美元额度；可通过 settings 的 `allocation_capacity:<subscription_type>` 调整。仅使用实时设备额度接口 `account_org_id` 指定的自有组织；加入的其他组织不刷新、不参与分配。自有组织未知或名额满时跳过该登录账号，不回退到其他组织。账号间仍按上述额度与用量策略均衡。

### 异步命令

Telegram 长轮询仅接收并分派命令。查询命令使用 4 个工作线程，`/sync` 使用独立单线程队列；登录、续费、撤销、保存账单、配置修改及多步输入使用有序写队列，避免状态竞争。查询与同步不会清除正在填写的账号流程，取消仍使用 `/cancel`。最多接受 64 个待处理任务，达到上限后暂停接收以限制内存。工作线程使用独立 SQLite 连接，失败回滚后关闭连接。停止服务时等待已接收任务完成（仍受 systemd 停止超时限制）。任务队列在内存中，进程崩溃不保证未完成命令恢复。

管理员 `/devices` 默认只显示 active 设备，`/devices all` 显示全部已采集设备（包括未绑定、missing/revoked 历史设备），按组织与设备 ID 去重，并优先显示自有组织登录入口。`/devices mine` 仅查看本人的 active 设备；普通用户始终只能查看自己的设备。列表自动分条发送，可先 `/sync` 刷新。`active` 表示登录有效，不表示设备实时在线。查看不会绑定或撤销设备。

设备最近使用时间取上游设备时间与已采集最后一次请求时间的较晚值，按组织 ID + 设备 ID 关联，跨采集入口共享，历史设备同样适用。此规则仅用于展示；没有任一时间来源时显示无记录，不将创建时间当作用量。自动撤销先排除最近 90 分钟（含边界）有真实请求的设备，再优先按上游闲置时间排序；无此类候选时按最早真实请求选择，后台心跳不阻止此回退。真实请求按组织和设备跨入口核对，撤销前补采并复查；采集失败或分页未完成则取消。只有主动下线可绕过请求保护，刚创建的设备也受 90 分钟保护。

`/report` 按“计费席位 × 订阅周期”分别发送账单，独立列出本期成本、各用户分摊和待认领金额；`/bill` 同样逐周期显示。日期参数只筛选相交周期，不将周期截成自然月。`/report save` 按订阅周期 ID 与用户分别保存快照，改变查询日期不会重复记账；刷新某期不覆盖其他周期。旧的月区间快照保留并标记 legacy。

管理员 `/quota [账号] [refresh]` 查询自有组织的 5 小时/7 天额度、快照时间和重置时间。窗口起点暂按重置时间减窗口长度推算，统计同组织、同上游账号从起点到快照时刻的已采集请求数、tokens、原始标价与按账单相同规则（精确→通配→默认倍率）计算的加权美元等值。满足快照 30 分钟内、流水水位覆盖快照且无分页欠账、使用率在 [5%,100%) 时，以加权用量÷使用率估算容量与剩余量。估算不保证覆盖其他客户端或未暴露流水，不代表官方美元额度，不参与分摊。细分模型额度只展示比例，不猜测模型映射。快照超过 30 分钟或缺失时自动 refresh，再同步流水到该快照时刻并补价；手动 `refresh` 也会补采。每组织刷新尝试间隔至少 30 分钟，失败沿用已有快照；空窗口不触发刷新。单次最多同步三轮，未完成分页或上游仍缺数据时说明原因，不编造估算。未定价请求不阻止估算，使用已知金额并标注遗漏条数及可能偏低。官方百分比和 tokens 不乘倍率；模型组合变化会影响容量估算。
